For designers working in Claude Desktop — any project

You never have to open Terminal.

This is a general-purpose version of this guide — it doesn't assume any particular repo, naming convention, or team setup. Use it for any project where you're connecting Claude Desktop to a GitHub repository that deploys through Netlify. You still never learn Git. You talk to Claude Desktop in plain English, and every phrase in a box below is something you can copy, paste into chat, and send exactly as written — just swap in your own project's names where noted.

Four boxes, one conversation. You only ever talk to the first one.

How the pieces fit together

On most teams, two things are already wired up before you touch anything: the project's code lives in a GitHub repository (a shared folder with a memory — every change, ever), and Netlify is already connected to that repository, so new work pushed to it gets a live, clickable preview automatically.

The one thing that's always yours to do is connecting Claude Desktop to your project folder. Once that's done, everything else — making a branch, saving your work, checking for other people's changes, getting a preview link — is a sentence you type into chat.

The one rule to remember: if a step ever sounds technical, it's not your step. It's the sentence you say to Claude so it can do the technical part.

Part one

One-time setup

You do this once, ever, per project. After today you'll never think about it again.

Get added to the GitHub repository

Ask whoever manages the project (your lead, or IT) to add your GitHub account as a collaborator on the repo. You can't skip this — it's the guest list, and Claude can't get you onto it.

Make an empty folder and connect it to Claude Desktop

No app to install. Create a new, empty folder on your computer somewhere memorable — like one called Projects — then, in Claude Desktop, open a Cowork session and connect that folder. This is the only "wiring" step that's actually yours to do — after this, Claude can read and write files in that project, and run the Git commands on your behalf.

Copy the repo's link from github.com

On the GitHub website, open the repo, click the green <> Code button, and copy the HTTPS link — it looks like https://github.com/your-org/your-repo.git.

Have Claude clone it into your folder

Paste the link into chat and ask Claude to clone it — that just means "download a real, connected working copy of the project" into the folder you just connected.

Say this to Claude
"Clone https://github.com/your-org/your-repo.git into this folder."
Private repo and Claude can't get in? On GitHub, go to Settings → Developer settings → Personal access tokens, generate one, and paste it in when Claude asks — a one-time step.

Say hello and check it worked

Say this to Claude
"What branch am I on, and is my folder connected to the GitHub repo correctly?"

If Claude answers with a real branch name (usually main), you're connected. If it says the folder isn't a Git repository, go back a step — the clone didn't finish, or you connected the wrong folder.

Check whether Netlify is already connected

On most existing projects, someone already did this before you arrived — that's the common case.

Say this to Claude
"Is there a netlify.toml file in this project, and can you tell if Netlify is already connected to this repo?"

Already connected? Skip ahead to Your daily loop — you're done here. Not connected yet? Keep going — the rest of this section walks you through setting it up yourself, once.

From here, it happens in your browser, not in chat. Signing into Netlify and authorizing GitHub access are things only you can click — Claude can prepare and push your code, but it can't log in on your behalf. About five minutes, once, and then it's permanent.

Log in to Netlify

Go to netlify.com. If your team already has an account, log into that one; otherwise sign up — "Continue with GitHub" is the fastest option and uses the account you already have.

Start a new site from your repo

Click this path Add new site → Import an existing project

Choose GitHub as the source

The first time you do this, Netlify will ask permission to access your repositories — click Authorize. If your repo doesn't show up afterward, its GitHub access may be scoped to only some repos — look for "Configure the Netlify GitHub App" in that same picker and grant it access to this one too.

Pick your repository

Find it in the list and select it.

Confirm the build settings

Netlify usually guesses these correctly. If you're not sure what to put in the build command or publish directory fields, ask Claude first.

Say this to Claude
"What's the build command and publish directory for this project, so I can enter them in Netlify?"

Deploy

Click this Deploy site

Netlify hands you a live URL right away (something like happy-lovelace-123.netlify.app) and starts the first build.

Done — and it stays done. That connection is now permanent. Every time you (or Claude, on your behalf) push to GitHub or open a pull request, Netlify rebuilds and updates the live site on its own. You will never need to click "deploy" again.
Part two

Your daily loop

This is the part you'll actually repeat, project after project. Each step is one sentence.

Start today's work on its own branch

A branch is your own private copy of the project to make changes in — nobody else's work moves until you decide to bring yours back in. Ask your team what naming convention they use (some teams use yourname/thing, others use feature/thing — either is fine, just be consistent).

Say this to Claude
"Make a new branch called jill/onboarding-screens from main and switch to it."

Pull in everyone else's latest changes

Do this at the start of every session, before you start editing — especially if it's been more than a day. This makes sure you're building on top of the newest version of main, not an old one.

Say this to Claude
"Pull the latest changes from main."

Build your thing

This is the actual design/dev work — describe the screen, component, or change you want, and Claude builds it in the project. If this team uses feature flags, ask what the convention is before you start; if not, don't worry about it.

Have Claude check your work

Before you save anything, ask it to run whatever checks this project has — the exact names vary by project, so let Claude find them.

Say this to Claude
"Find and run this project's tests, type checks, and linter, and tell me if anything fails."

Save your work and send it up

A commit is a labeled save point — a snapshot of what changed, with a short note about why. A push sends that snapshot from your computer up to GitHub, where Netlify can see it. You almost always do both in the same breath.

Say this to Claude
"Commit everything and push it to jill/onboarding-screens."

If your branch has fallen behind, catch it up

While you were working, other people may have pushed their own changes to main. If Claude ever mentions your branch is "behind," or if you're about to open a pull request and want a clean history, ask for a rebase — it replays your changes on top of the newest main, so your branch looks like it started from today, not last week.

Say this to Claude
"Rebase my branch on top of the latest main."
If two people changed the same lines, Claude will flag a conflict and ask you which version to keep. That's normal — see "If something looks wrong" below.

Open a pull request

A pull request (or "PR") is the formal ask to bring your branch's changes into main — it's where your team reviews and comments before anything merges. Most projects on GitHub + Netlify auto-post a "Deploy Preview" comment on the pull request within a minute or two of you opening it.

Say this to Claude
"Open a pull request from jill/onboarding-screens into main, with a short description of what changed."

Get your preview link and share it

Check the pull request page on GitHub for a comment from the Netlify bot — that comment holds your live "Deploy Preview" link. Share that link (and the pull request itself) with whoever needs to look at your work.

Say this to Claude
"Has Netlify posted a preview link on my pull request yet? If so, what's the link?"
What you'll never do: open Terminal, type git anything yourself, or run the site on your own computer to see your changes. The deploy preview is your preview.
Plain-English dictionary

The words that matter

repo
Short for "repository" — the shared project folder, plus its entire history of changes. Lives on GitHub.
branch
Your own private copy of the project to work in. Changes on your branch don't affect anyone else's until you bring them together.
commit
A labeled save point — a snapshot of exactly what changed and why, at that moment.
push / pull
Push sends your saved snapshots up to GitHub. Pull brings other people's snapshots down to you. Same road, opposite directions.
rebase
Replays your changes on top of the newest version of main, so your branch's history reads cleanly, as if you'd started today.
merge conflict
Two people changed the exact same lines. Nothing is broken — Claude will show you both versions and ask which one to keep.
main
The one branch that represents "the real, current project." Everyone's work eventually joins back into it.
pull request (PR)
A formal request to merge your branch into main — the place your team reviews, comments, and approves before anything ships.
Netlify build / deploy preview
Every time a branch is pushed (and usually when a pull request opens), Netlify automatically assembles it into a real, clickable website — that link is your preview.
When something looks wrong

You didn't break it

? Claude says there's a "merge conflict." Did I break something?
No — it means two people edited the same lines, and Claude wants a human decision. Ask it: "Explain the conflict in plain English, and show me both versions." Then just tell it which one to keep, or how to combine them.
? I opened a pull request, but there's no preview link yet.
Builds usually take a minute or two. Ask: "Is the Netlify build for my pull request still running, or did it fail?" If it never shows up at all, this repo may not be connected to Netlify yet — see One-time setup above and connect it.
? My branch says it's "behind main" — is that bad?
It just means someone else pushed changes after you started. It's completely normal. Ask Claude to rebase (see above) whenever you notice it, or right before you open your pull request.
? I think I asked for the wrong thing and now something's messed up.
Git almost never actually loses work. Say: "Something looks wrong — don't push or delete anything, just tell me what state my branch is in." Claude can look before it touches anything.
? Do I ever need to touch GitHub.com directly?
Rarely. The main reasons are getting added as a collaborator at the start, and sometimes reading a review comment someone left on your pull request. Everything else goes through chat.

Every team names branches a little differently and runs slightly different checks — when in doubt, ask Claude to look at the project first ("how does this project usually name branches, and what commands does it run to check code?") rather than guessing.
